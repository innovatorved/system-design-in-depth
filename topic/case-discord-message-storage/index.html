Intuition first

A chat app's message store is like a post office with one pigeonhole per conversation. Most pigeonholes get a letter a week; a few, for huge public channels, get thousands a minute and everyone reads them at once. The building must be designed for both: many quiet boxes that are cheap to keep, and a handful of boxes so busy that everyone crowds around them.

Mental model: partition messages by (channel, time bucket) so partitions stay bounded, keep them sorted by a time-ordered id so "latest 50" is a sequential read, and protect hot partitions with a service layer that coalesces identical reads.

  • Trap: thinking bucketing fixes hot channels. It bounds partition size over time, but the current bucket of a viral channel still lands on one replica set.
  • Trap: blaming only Java GC. Compaction backlog, tombstones and reads of cold data also drove latency; ScyllaDB helped, and so did the data services.
  • Trap: calling it a pure database swap. The migration also changed the service layer and routing.

Case: How Discord Stores Trillions of Messages

A message store has to serve both a crowded channel with thousands of active chatters and a quiet direct message conversation whose latest messages are months old. Discord's database history shows why those two reads stress different parts of the same system.

Discord started with MongoDB, migrated to Cassandra to handle billions of messages, and more recently migrated to ScyllaDB to handle trillions. The evolution is a masterclass in understanding database architectures.

The Migration to Cassandra

Starting around late 2015, after reaching about 100 million stored messages, Discord moved from MongoDB to Cassandra (the move was described in a January 2017 blog post). They needed a database that provided linear scalability, high availability, and fast writes. Cassandra, a wide-column NoSQL store, fit the bill perfectly because of its LSM-tree architecture, which makes writes incredibly fast.

Discord's published Cassandra design bounded partitions with a composite partition key such as (channel_id, bucket) and ordered messages by a timestamp-bearing message_id. Replication placed each partition on multiple nodes; bucketing limited partition size but did not spread one currently hot bucket across many write owners.

Partition Size and Hot Buckets

Time buckets keep a channel's lifetime history from becoming one unbounded partition and let old buckets age independently. They do not solve every hot-key problem: all writes for one channel's current bucket still target that partition's replica set. A sudden viral channel can therefore overload its current owners until the workload is further sharded, buffered, or moved.

Read Performance and Garbage Collection

Cassandra is written in Java. As Discord scaled to trillions of messages, the Java Garbage Collector (GC) became a massive bottleneck. When GC paused the application to clean up memory, latency spiked across the cluster, causing cascading timeouts.

Furthermore, reading old messages required waking up disks and reading multiple SSTables (immutable data files on disk). To mitigate this, Discord built Rust-based data services in front of the database that route requests by channel and collapse multiple simultaneous queries for the same data into a single database query (request coalescing); they are a traffic-shaping layer, not a cache.

The Move to ScyllaDB

Ultimately, Discord migrated from Cassandra to ScyllaDB. ScyllaDB's C++ shard-per-core architecture avoids JVM garbage-collection pauses and offers substantial CQL compatibility, but predictable latency still depends on compaction, disks, caching, repair, and data modeling. Discord also changed service and query behavior during the migration; compatibility did not make the systems operationally identical.

Worked example: why buckets bound partitions

A busy channel receives 200 messages per minute of about 1 KB. Unbucketed, one year is 105 million messages, about 105 GB in a single Cassandra partition, which is far beyond the range where compaction and repair behave well. With 10-day buckets, each partition is about 2.9 million messages, around 3 GB for this extreme channel, and small for nearly every other channel. Reading the latest messages touches only the newest bucket (and occasionally the previous one).

Request coalescing in the data services

sequenceDiagram participant U1 as User A participant U2 as User B participant DS as Channel data service participant DB as ScyllaDB U1->>DS: latest 50 messages in channel 42 U2->>DS: latest 50 messages in channel 42 DS->>DB: one coalesced query DB-->>DS: rows DS-->>U1: rows DS-->>U2: same rows

Requests are routed by channel id (consistent hashing) so all requests for one channel reach the same data service instance, which can then merge identical in-flight queries. When a huge server announces something and 100,000 clients open the channel, the database sees a handful of queries instead of 100,000.

Lessons that transfer

  • Model partitions for bounded size and for the dominant read ("latest N").
  • Put a thin, stateless-looking but routing-aware service in front of the database to absorb thundering herds.
  • Migrations of this size need a purpose-built, restartable, checkpointed copier and a validation pass comparing reads from both clusters.

Buckets stop a channel's lifetime history becoming one unbounded partition, but every write in the current window still hits the same partition's replicas. Believing buckets spread hot traffic is the trap the lesson names explicitly.

A channel receives 600 messages per minute of about 1 KB each. Roughly how large is one 10-day bucket, and how large would an unbucketed year be?

600 x 1,440 minutes x 10 days is about 8.6 million messages, roughly 8.6 GB per bucket, while a year is about 315 million messages or 315 GB in one partition. The last option mistakes the yearly total for ten buckets instead of about 36.
Why route by channel staff
From: Request coalescing in the data services

Discord's data services coalesce identical in-flight queries. Why must requests be routed to instances by channel ID rather than spread by a round-robin load balancer?

Coalescing merges queries that are simultaneously in flight within one process, so 100,000 requests for channel 42 must converge on one instance to become a handful of database reads. Caching is the tempting answer, but the lesson stresses these services shape traffic and are not a cache.

Key Takeaways

Wide-column stores (Cassandra/Scylla) excel at high-throughput write workloads due to LSM trees.
Partitioning by channel keeps related data together but creates Hot Partitions for viral channels.
Time buckets bound partition size and distribute historical buckets over time, but the current bucket can remain hot.
Runtime and storage-engine behavior matter at extreme scale; avoiding JVM GC was one benefit of Discord's move to ScyllaDB.
Coalescing concurrent reads at the application layer protects the database from thundering herds.
