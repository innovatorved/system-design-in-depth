Intuition first

Imagine a house with five smoke detectors, and during a real fire you discover that one had no battery, one was never installed, one was disconnected, one was ringing in an empty room, and one only worked if someone happened to be standing next to it. Having five detectors felt safe; nobody had ever pressed the test button.

Mental model: a backup you have not restored is a hypothesis. Recovery point (how much data you can lose) and recovery time (how long restore takes) are only known once you rehearse them.

  • Trap: counting backup mechanisms instead of tested restores. GitLab had several; none worked reliably when needed.
  • Trap: silent failures. The pg_dump job failed every run, and its alert emails were rejected, so nobody knew.
  • Trap: blaming the engineer. Tired people type into the wrong terminal; the fix is guard rails, distinct prompts and runbooks, not blame.

Case: GitLab's Database Incident

On January 31, 2017, GitLab suffered a major incident that resulted in the deletion of production database data. Service returned the next day using an older copy, leaving about six hours of database changes unrecovered. The postmortem is a vital lesson in operations, fatigue, and backup strategies.

The incident wasn't caused by a malicious hacker or a complex software bug; it was a cascading series of operational failures, exacerbated by human fatigue, culminating in an engineer accidentally running rm -rf on the primary production database instead of a misbehaving replica.

The Anatomy of the Outage

GitLab was experiencing high load caused by spam accounts, causing the PostgreSQL primary database to struggle. A secondary replication node fell far behind. An engineer decided to wipe the lagging secondary node and restart the replication process from scratch.

The engineer opened multiple terminal windows. Due to exhaustion (it was late at night) and identical terminal prompts, the engineer typed rm -rf /var/opt/gitlab/postgresql/data in the terminal connected to the primary production node, not the secondary node.

They realized the mistake seconds later and hit Ctrl+C. The production directory was roughly 300GB, and by the time the command was stopped around 300GB had already been removed (only about 4.5GB was left), so recovery had to use an older copy.

The Backup Failures

Accidental deletions happen. This is why we have backups. But when GitLab tried to restore from backups, they discovered a catastrophic truth: of their five backup and replication safety nets, most had silently failed or were not in use, and the only usable copy was a manual LVM snapshot taken by chance.

flowchart TD Disaster["Production Data Deleted"] --> B1{"Replica db2?"} B1 -- "Being rebuilt" --> B2{"pg_dump Backups?"} B2 -- "Failing silently" --> B3{"Azure Disk Snapshots?"} B3 -- "Not enabled for DB servers" --> B4{"S3 Backups?"} B4 -- "Empty" --> B5{"LVM Snapshots?"} B5 -- "Manual snapshot, about 6 hours old" --> Recovery["About 6 Hours of Data Lost"]
  • Automated pg_dump: The cron job was failing silently because it was using an incompatible version of pg_dump.
  • Azure Disk Snapshots: These were not enabled for the database servers.
  • LVM Snapshots: Taken only once every 24 hours; the copy that saved them was a manual snapshot an engineer happened to take about six hours earlier to refresh staging.
  • Streaming Replication: Fragile and poorly documented; the lagging replica was the very thing being rebuilt when the deletion happened.
  • S3 Backups: The S3 bucket where backups were supposedly being sent was empty.

They eventually restored the database using a manual LVM snapshot of the production database taken about six hours earlier and loaded into the staging environment for load testing; copying it back from staging took around 18 hours. Six hours of user data (issues, merge requests, comments) was permanently lost.

The Lessons Learned

The incident highlighted the stark difference between "having backups" and "having a tested recovery process". Data doesn't exist unless it has been successfully restored.

It also brought attention to operability. Production systems must have safeguards against human error, visual indicators of which environment a terminal is connected to, and blameless postmortem cultures. GitLab famously live-streamed their entire recovery process on YouTube, setting a new standard for transparency in the industry.

Database data from roughly six hours was lost, which GitLab estimated at about 5,000 projects, 5,000 comments and 700 new user accounts. Git repositories and wikis themselves were not lost, though some were orphaned from their database records.

S3 bucketEmpty, because the dumps never succeeded
Azure disk snapshotsEnabled for the NFS server but not for the database servers

Turning it into practice

  • Restore drills: automatically restore the latest backup to a scratch host on a schedule and run sanity queries; page when it fails.
  • Point-in-time recovery: continuous WAL archiving (for example WAL-E or WAL-G, which GitLab adopted) lets you recover to the minute before a mistake.
  • Guard rails: different prompt colors for production, confirmation for destructive commands, and delayed deletion (move aside, delete later).
  • Measure RPO and RTO: GitLab's restore took around 18 hours partly because of slow disk throughput, something only a rehearsal would have revealed.

The usable snapshot was taken at about 17:20, the deletion happened at about 23:25, and GitLab.com was back online at about 18:00 the next day. What were the effective RPO and RTO?

Data loss ran from the 17:20 snapshot to the 23:25 deletion, about 6 hours, and downtime ran from the deletion to about 18:00 the next day, about 18.5 hours. The 24.5-hour figure measures from the snapshot rather than from the incident, which confuses the two objectives.
Why pg_dump failed silently recall
From: What each safety net actually did

GitLab's automated pg_dump backups had been failing for some time, yet nobody knew. What combination caused this?

The job used an incompatible binary, so every run failed, and the failure notifications were bounced, so the failure was invisible; the empty S3 bucket was a consequence, not the cause. This is why the lesson says to monitor backups as rigorously as production.
The drill that finds everything staff
From: Turning it into practice

GitLab had five safety nets that failed in five different ways. Which single practice would most likely have exposed all of those weaknesses before the incident?

Restore drills test the outcome that matters, so a failing dump, an empty bucket and slow copy speed would all surface, along with real RTO. Another mechanism is the tempting answer, but GitLab's lesson is that untested mechanisms add a feeling of safety, not recoverability.

Key Takeaways

A backup system is useless if you have not routinely tested the restoration process.
Monitor your backup jobs just as rigorously as you monitor your production application.
Human error under fatigue is inevitable; design systems with 'undo' buttons, delayed deletions, or strict blast-radius controls.
Use visual cues (different colored terminal prompts) to distinguish production servers from staging or replicas.
Blameless postmortems and transparency build trust faster than hiding mistakes.
