Intuition first

File sync works like a shared recipe binder kept in sync between several kitchens. Nobody photocopies the whole binder when one page changes. Each page has a fingerprint (a chunk hash), and a kitchen only sends the pages whose fingerprints the head office does not already have. Head office keeps the table of contents (metadata: which pages, in which order, make up version 7 of the binder), and rings the other kitchens to say "version 7 is out". If two kitchens edited the same page while offline, head office keeps both versions and marks one as a conflicted copy.

Mental model: a file is a list of content-addressed blocks. Syncing means exchanging block lists and uploading only the missing blocks. A monotonically increasing server revision (a cursor) tells each device what it has missed.

  • Trap: using timestamps to decide the latest version. Device clocks drift. Use server-assigned revisions, and send the base revision with each edit to detect conflicts.
  • Trap: fixed-size chunks for all edits. Inserting one byte at the start shifts every boundary. Content-defined chunking (rolling hash) keeps most chunks unchanged.
  • Trap: global deduplication without thinking about privacy. "Upload skipped, we already have this" reveals that someone else stores the same file. Deduplicate per user, or require proof that the client actually has the content.

Designing a File Sync Service (Dropbox/Google Drive)

A file-sync service carries changes between a remote folder and devices that may be offline. It has to move the right bytes, distinguish an edit from a retry, and preserve work when two devices change the same file.

The core challenge is minimizing bandwidth and ensuring consistency across multiple devices (laptops, phones) that might go offline and come back online at random times.

Block-Level Sync (Chunking)

If a user changes one line in a 100MB file, uploading the whole file may be inefficient. A client can hash chunks and upload only missing content. Fixed 4MB boundaries work well for aligned replacements, but an insertion near the beginning shifts later boundaries and can make most blocks appear new; content-defined chunking trades more CPU for boundary stability.

This is called block-level sync. The backend object storage doesn't store files as monolithic blobs; it stores these 4MB chunks, named by their cryptographic hash (Content-Addressable Storage). The metadata database maps a file version to an ordered list of chunk hashes.

Deduplication

Content hashes make deduplication possible, but global cross-user deduplication is a security and lifecycle choice rather than an automatic consequence. The service must authorize every reference, avoid revealing whether another account owns a guessed hash, count references safely, and delete a block only after no retained version is entitled to it. Per-tenant deduplication is a simpler isolation boundary.

The Architecture

A typical architecture splits metadata and block storage:

flowchart TD Client["Desktop Client"] BlockServers["Block Servers"] MetadataServers["Metadata Servers"] Notification["Notification Service"] Client -->|Upload Chunks| BlockServers BlockServers --> S3[("Object Storage")] Client -->|Update File Info| MetadataServers MetadataServers --> DB[("Metadata DB")] MetadataServers --> Notification Notification -->|Ping| Client

Synchronization Protocol

Clients need to know when files change on the server. Polling the server every second drains battery and wastes server resources. Instead, clients maintain a long-lived connection (like WebSockets or Long Polling) to a Notification Service.

When Laptop A uploads a change, it updates the Metadata DB. The Metadata Service publishes an event to the Notification Service, which instantly pings Laptop B: "There is a new version of 'document.docx'". Laptop B then requests the new metadata and downloads only the missing chunks from the Block Servers.

Handling Conflicts

If Laptop A and Laptop B both edit the same file while offline, and then both come online, we have a conflict. The system cannot merge the files itself (it doesn't know the business logic of a Word document). The standard approach is to accept both files, creating a "Conflicted Copy" of the second file to arrive, and relying on the user to resolve it.

Worked example: editing a 100 MB file

  • The file is split into 25 chunks of 4 MB. Dropbox has used 4 MB blocks with SHA-256 hashes.
  • The user appends 1 MB to the end. Only the last chunk changes (and possibly one new chunk is added), so the client uploads about 4 to 5 MB instead of 100 MB.
  • The user inserts 1 KB near the start. With fixed chunks every boundary shifts, so all 25 hashes change and about 100 MB is uploaded again. With content-defined chunking (a rolling hash picks boundaries where the hash matches a pattern, averaging about 4 MB), only the chunk containing the insertion changes, so about 4 MB is uploaded.
  • The metadata commit is a small request: file_id, base_rev 17, new block list [h1, h2, ...]. If the server's current revision is not 17, the commit is rejected and the client handles it as a conflict.

Sync protocol

sequenceDiagram participant A as Laptop A participant M as Metadata service participant B as Block service participant N as Notifier participant L as Laptop B A->>M: which of h1 to h26 are missing M-->>A: missing h25, h26 A->>B: upload h25, h26 A->>M: commit file 9, base rev 17, blocks h1 to h26 M-->>A: ok, rev 18, cursor 5012 M->>N: namespace changed N-->>L: wake up L->>M: list changes since cursor 5011 M-->>L: file 9 rev 18, blocks h1 to h26 L->>B: download h25, h26 only

Commit the metadata after the blocks are durable, so no device ever sees a version whose blocks are missing. Blocks that are uploaded but never committed are removed later by a garbage collector.

Check yourself Question 1 of 3
Offline edit conflict recall
From: Designing a File Sync Service (Dropbox/Google Drive)

Two laptops edit the same .docx while offline and both come online. What is the standard way a file-sync service handles this?

The service cannot merge an opaque binary format safely, so it preserves both and lets the user resolve the conflicted copy. Picking the later timestamp silently loses work, and device clocks drift so the later timestamp may not even be the later edit.
Insert near the start apply
From: Worked example: editing a 100 MB file

A 200 MB file is stored as 4 MB chunks. The user inserts 2 KB near the beginning. Roughly how much is uploaded with fixed-size chunks versus content-defined chunking?

With fixed boundaries the insertion shifts every later chunk, so all 50 hashes change and the whole file is re-sent. A rolling hash re-anchors boundaries to content, so only the chunk containing the insertion changes. Fixed chunks work well only for appends or in-place replacements.
Dedup leaks information staff
From: Chunking and sync choices

With global cross-user deduplication, an upload of a known leaked document completes instantly with upload skipped. Why is this a problem, and what is the safer design?

An instant skip is an oracle telling an attacker that someone else has the file, so global dedup trades storage savings for privacy. Per-user or per-team scope, or proof that the client actually holds the bytes, closes the leak. The other options describe unrelated concerns.

Key Takeaways

Break files into chunks to only upload/download the parts of a file that actually changed.
Use Content-Addressable Storage (naming chunks by their hash) to achieve automatic deduplication.
Separate the metadata path (database) from the data path (object storage).
Use long-polling or WebSockets to notify clients of changes instantly, avoiding inefficient polling.
Handle offline conflicts gracefully by creating conflicted copies rather than silently overwriting data.
