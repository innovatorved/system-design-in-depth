Intuition first

Imagine ordering a book from a warehouse across the ocean. Even if the warehouse packs your box in one second, the ship still has to cross the water—and before it even packs the box, you have to exchange three letters just to agree on the address and payment. That is what a browser does when a user in Mumbai or Sydney loads a web page hosted in Virginia.

Mental model: fiber optic light travels at roughly 200 kilometers per millisecond, and a single page load needs multiple sequential round trips (TCP, TLS, HTML, then render-blocking CSS and the hero image). Caching at an edge Point of Presence (PoP) moves both the handshake and the bytes into the user's own city, turning a 2-second blank white screen into a sub-250ms paint.

  • Caching only images and JS leaves TTFB slow. The browser cannot even discover your CSS or hero image until the HTML arrives. If HTML still crosses the ocean, Largest Contentful Paint (LCP) stays high.
  • Even a cache MISS at the edge is faster than direct-to-origin. Terminating TCP and TLS at the local PoP and reusing warm keep-alive connections to the origin saves two full transoceanic round trips.
  • Shared edge caches amplify personalization mistakes. Caching a response that contains a user's session cookie or private header without Cache-Control: private or proper cache keys can leak one user's page to everyone in that city.

Speed of Light & Why 1 RTT Turns Into 5

System design benchmarks often report origin server latency in isolation: “our API responds in 40 ms.” Yet a user in Mumbai or Sydney opening that same page hosted in us-east-1 (Virginia) stares at a blank screen for over two seconds. The culprit is physics multiplied by protocol waterfalls.

Light travels through glass fiber at roughly 200 km/ms (about 1.5× slower than in vacuum), and real internet cables do not follow straight great-circle paths (add ~1.25×–1.35× routing stretch plus router switching). A 12,800 km fiber path from Mumbai to Virginia therefore has a physical round-trip time (RTT) of roughly 170–220 ms. Before a browser paints a single pixel over HTTP/2, it pays that RTT sequentially:

  1. TCP Handshake (1 RTT): SYN → SYN-ACK → ACK across the ocean (~200 ms).
  2. TLS 1.3 Handshake (1 RTT): Cryptographic negotiation (~200 ms; HTTP/3 QUIC merges TCP+TLS into 1 RTT).
  3. HTML Request & TTFB (1 RTT + Origin SSR): Request travels to origin, origin queries DB and renders HTML (e.g., 140 ms), response returns (~340 ms). Total TTFB is already ~760 ms.
  4. Critical Subresources (1+ RTT): Only after parsing the HTML does the browser discover render-blocking CSS and the hero image, paying another full ocean RTT (~200 ms) plus transfer time before First Contentful Paint (FCP) and Largest Contentful Paint (LCP).

What Edge Caching Actually Moves Closer to the User

1. Local TCP & TLS Termination (Wins Even on a Cache MISS)

Anycast BGP routes the user to a Point of Presence (PoP) 10–20 ms away. Both TCP and TLS 1.3 complete locally in ~25 ms instead of ~400 ms. Even when the requested page is a cold MISS, the PoP forwards the HTTP request over a pre-warmed, persistent keep-alive connection pool to the origin, eliminating cross-ocean handshakes.

2. Static Assets vs. Full-Page HTML Caching

Putting only JS, CSS, and images on a CDN is the most common half-measure. While subresources load quickly, the HTML document still crosses the ocean and runs origin rendering. Because HTML is the root of the browser's critical rendering path, caching public HTML at the edge using s-maxage is what collapses TTFB from 800 ms to under 40 ms:

Cache-Control: public, max-age=0, s-maxage=60, stale-while-revalidate=300, stale-if-error=86400
  • max-age=0 tells the user's browser to revalidate with the nearest PoP (so purges take effect immediately).
  • s-maxage=60 tells shared edge caches (CDNs) to serve the HTML fresh for 60 seconds.
  • stale-while-revalidate=300 lets the PoP serve a slightly expired response in ~18 ms while refreshing from the origin asynchronously in the background—hiding ocean latency from the user completely.
  • stale-if-error=86400 keeps serving the last good cached HTML if the origin suffers an outage.

3. Tiered Caching & Origin Shielding

A global CDN may run 300+ PoPs. If every PoP independently fetches from your origin on a cold start or after a cache purge, a single popular page triggers 300 origin renders. Tiered Caching (Origin Shield) places a small set of regional mid-tier caches in front of the origin. The first PoP miss populates the shield; the other 299 PoPs hit the shield instead of waking your origin database.

What You Can (and Cannot) Cache at the Edge

  • Ideal for Edge HTML: Marketing pages, documentation, news articles, e-commerce product/catalog pages, public profiles, and read-heavy JSON APIs.
  • Split Shell + Dynamic Islands: When a product page is 95% public but shows a personalized “Cart (2)” badge, cache the public HTML shell at the edge and hydrate the small user-specific fragment via an authenticated API call or Edge Worker (Edge Side Includes).
  • Never Cache at Shared Edge: Account settings, checkout/payment state, private messages, or any response carrying user-specific PII—always emit Cache-Control: private, no-store.

Production Failure Modes

  • Cache Key Fragmentation: Emitting Vary: User-Agent or including marketing query parameters (utm_source, fbclid) in the cache key creates thousands of near-identical variants, collapsing hit ratio from 95% to under 10%.
  • Cookie-Induced Cache Bypasses: Many CDNs automatically bypass the cache whenever a request carries a Cookie header. Strip analytics cookies at the edge before cache lookup for public routes.
  • Global Purge Storms: Issuing a wildcard purge (/*) across 300 PoPs simultaneously creates a thundering herd against your origin. Use surrogate keys (cache tags), Origin Shielding, and request coalescing so only one fetch per key reaches the origin.

Key Takeaways

Speed of light in fiber (~200 km/ms) multiplies across sequential TCP, TLS, HTML, and subresource round trips, turning a 40ms origin into a multi-second page load for distant users.
Terminating TCP/TLS at the nearest Anycast Edge PoP cuts latency even on a cache MISS via warm Edge-to-Origin keep-alive connections.
Caching only static assets still leaves HTML TTFB bottlenecked by ocean RTT; combining s-maxage with stale-while-revalidate collapses both TTFB and LCP.
Use Origin Shielding (tiered caching), cache tags, and normalized cache keys to prevent cold-miss storms and avoid leaking personalized responses.
